# 4.4 Implementation of the Selected Design

## 4.4.1 Detector Training

Each detector candidate was fine-tuned end to end with a cross-entropy loss over the 32 emotions, under the settings of Table 4.6. Training runs for at most four epochs with early stopping after one epoch without improvement, and the checkpoint reported is the one with the best validation accuracy rather than the last, so that a run that begins to over-fit is not the run that gets measured. The learning rate warms up linearly over the first 6% of steps: this is RoBERTa's own fine-tuning setting, and it is not cosmetic, since without it the RoBERTa-large run diverged to 5.0% accuracy before the cause was found (Section 3.7). Mixed 16-bit precision and gradient accumulation keep the effective batch at 16 inside 8 GB of memory. Every run uses seed 42, and all five candidates were trained by the same script with only the model name changed, so the comparison in Chapter 5 is between architectures and not between training recipes.

## 4.4.2 Generator Configuration

The generator is never trained in the final system: it is used zero-shot and steered entirely by its system prompt. Two implementation decisions make that practical within the memory budget. The model is loaded with 4-bit NF4 quantisation, double quantisation and 16-bit computation {cite:dettmers2023qlora}, which keeps the quality of 16-bit weights at about a quarter of the memory. And decoding is fixed for every system in the thesis, with sampling at temperature 0.7 and top-p 0.9 rather than greedy or beam search, which are known to produce repetitive text {cite:holtzman2020}. Table 4.7 lists the settings; because they are identical everywhere, any difference between systems comes from the design rather than from decoding.

## 4.4.3 Implementing the Two Stages

Stage 1 issues a greedy call of at most ten tokens and parses the answer by matching it against the three candidate names; anything unmatched falls back to the detector's top choice. Stage 2 builds the system prompt in the fixed order of Figure 4.4 and issues a sampling call of at most 250 new tokens, well above the prompt's request for under 100 words, so that no reply is cut off mid-sentence; the longest reply the final system produced reached 119 tokens. Three model-specific details had to be handled explicitly and are the kind of thing that silently corrupts results if missed: Phi-4-mini's end-of-turn token differs from its end-of-text token, so generation must stop on the former; Gemma's chat template has no system role; and Phi-4-mini merges its attention projections into a single layer, which matters when naming the modules that low-rank adaptation should target.

## 4.4.4 Implementing the Baselines

The monolithic baselines share the pipeline's scaffolding so that only the intended difference remains: the same 300 conversations, the same decoding settings, the same rule checks and the same output format, with the detector removed and the prompt asking the model to work out the feeling itself. The LoRA baseline is the one design that trains a generator, using rank 16 and alpha 32 on the attention projections with a learning rate of 2e-4, values drawn from the original low-rank adaptation work {cite:hu2022lora}. Its implementation carries one correction worth recording: the padding token must be the model's end-of-text token, because using the end-of-turn token as padding removes that token from the loss, and a model that never sees it learns not to stop. The first version of this baseline had that defect, it was retrained once the cause was found, and every affected number was replaced (Section 5.3.5).

## 4.4.6 Verification and Safeguards

Every design was functionally verified on a small trial run before any full evaluation, to confirm that outputs were well formed and that the model-specific details above were handled. Two automatic safeguards then protect the selected design in normal operation: execution halts if the detector returns no attention weights, so the cue mechanism cannot silently degrade, and every stage-1 decision is written to the output file, so that a malformed emotion choice would be visible rather than absorbed by the fallback. Scored outputs for all 4,200 generated replies are kept in the repository, which is what allows every table in Chapter 5 to be regenerated by script rather than copied by hand.
