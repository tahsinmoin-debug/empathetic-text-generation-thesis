\section{Design Process or Methodology Overview}
\label{sec:4.1}

This chapter explains the design of the system and reasons for the form it assumes. The target is a response that makes a person feel understood, generated by a single 8 GB consumer GPU, and with the emotional evaluation performed and documented, not buried in a model. The guidelines for every decision were: \textbf{recognizing the feeling before writing anything}, so that the emotional judgement is an object separate from the writing, and \textbf{giving the generator one instruction at a time}, because if it is told to respond to several feelings at once, it responds well to none of them, and \textbf{not adopting anything that the measurements don't support}, so that each alternative is simulated on the same conversations, and each is kept only on evidence. This work was done in two consecutive phases. The first developed and evaluated an emotion detector using five emotion detector architectures on the texts received by the system. The second constructed the response side on top of that detector, and compared generators, four methods of getting the detector output to the generator, and a set of monolithic baselines, that respond without any detector at all. The loop that controlled both stages is shown in figure 4.1.

\subsection{The Proposed System}

The last system is a two-stage pipeline with two models, as illustrated in Figure~\ref{fig:4.2}. There is a purpose for every part.

\begin{itemize}
  \item \textbf{d1, the emotion detector:} reads the user's message, in conversation the last four turns of the user and outputs a probability for all the 32 emotions in EmpatheticDialogues \cite{rashkin2019} using a RoBERTa-base encoder fine-tuned on the 32 emotions. Only its three most probable emotions leave this stage.  Using an encoder instead of a prompted generator is preferred since almost nothing was found to be more effective at emotion recognition than encoders fine-tuned for the task \cite{belay2025} and encoders are less costly than generators, requiring only 125 million parameters, while a generator has 3.8 billion parameters.
  \item \textbf{Attention cues}: the words that the detector learned on, from its last layer of attention, from the same forward pass. These are conveyed to pass the information on so that a response may refer to the actual writing and not just the emotion word label.
  \item \textbf{}         \textbf{Stage 1, emotion choice: }In the short and deterministic call, the generator, Phi-4-mini-instruct \cite{abouelenin2025phi4mini} is instructed to choose the most suitable emotion from among three options proposed by d1 to match the message. This resolves the detector's uncertainty prior to any reply being written and is the step that allows the pipeline to benefit from three candidates without being confused with three sets of instructions.
  \item \textbf{}         \textbf{Prompt builder:}The selected emotion activates one of 32 pieces of guidance that are written with that emotion in mind and is added to the cue words and the three response rules, making up a single system prompt.
  \item \textbf{Stage 2, reply generation:} The same generator loaded in 4-bit form writes the written reply to the last ten exchanges of the conversation.
\end{itemize}
All intermediate decisions are documented and shown along with the three candidates' confidences, the final emotion used, and the cue words. That record is what a single end to end model can't produce and that is why the design keeps the two jobs separate.

\subsection{Design Space Explored}

This thesis is about the question of whether or not the separation described above is merited. The methodology is designed to test that question, not to presume the answer, and thus the design space includes designs that would render the detector unnecessary. Four families of alternatives were put in place and simulated in the same conditions:

\textbf{Detector alternatives:} one decoder and four encoder models trained with the same data and the same settings (Section 4.2.1).

\textbf{Generator alternatives: }three instruction-tuned generators with 1.5 to 4 billion parameters, detector and prompt and conversations are fixed (Section 4.2.2).

\textbf{Integration Alternatives:} 4 types of integration of d1's output into d2's input, and the two-stage design that was finally adopted (Section 4.2.3).

\textbf{Monolithic and retrieval alternatives:} five designs that answer without an additional detector, and one that retrieves human examples instead (Section 4.2.5).

All of these were run using the same 300 held-out conversations with the same decoding settings, so the differences are due to the design and not the data or sampling. The results of their work are reported in Chapter 5; this chapter identifies what each design is. 

\subsection{Evaluation Strategy}

Since there are no automatic measures that capture empathy, each design will be evaluated on five independent signals: rule adherence (automatically checking if a reply acknowledges the feeling, asks exactly one question, and is within 120 words); the WASSA 2024 empathy classifier; emotion validation (checking whether the emotion expressed in the reply matches the actual label of the conversation); two AI judges from unrelated developers rated ``blind'' to the study; and a forced-choice study with human raters. The top-1 accuracy, top-5 accuracy and macro-F1 on the complete test partition are used as separate criteria for detector candidates. Each system is asked the same questions, and the comparisons are made using paired methods: paired McNemar's exact test for binary outcomes \cite{mcnemar1947}, paired Wilcoxon signed-rank test for scores \cite{wilcoxon1945}, bootstrap confidence intervals with 10,000 resamples \cite{efron1993} and Holm correction across families of comparisons \cite{holm1979}. Only differences with a corrected p-value < 0.05 and a confidence interval not containing zero are considered to be significant. 

\subsubsection{Selection of the AI-Judge Panel}

While language models are known to be imperfect evaluators, with more than 80\% agreement with human evaluators \cite{zheng2023judge}, their use is well-established, and the panel was specifically designed against this. Because LLM evaluators recognise and favour their own outputs \cite{panickssery2024}, the judges come from developers unrelated to every model being judged: \textbf{Nemotron 3 Ultra} (NVIDIA) and \textbf{gpt-oss-120b }(OpenAI), neither of which shares a family with our generator (Microsoft) or with the Qwen baselines (Alibaba). The reported score is the average of the two scores from the two panels from different families as there is less bias in a panel of different families than in a panel consisting of one large judge \cite{verga2024}. Each judge rates empathy and relevance and safety (on a scale of 1-10) against written anchors at temperature 0, only seeing the user's message and one reply, not the system's name or the human reference. All responses for all judged systems were scored by both judges. The panel is described in Table~\ref{tab:4.1}.

\subsubsection{Use of the WASSA Empathy Classifier}

Replies are independent of the rule checks and the judges, and are evaluated by the hyy33 system from the WASSA 2024 shared task \cite{yang2024hyy33}. It suits this project because it was trained on third-party human empathy ratings of individual conversation turns \cite{giorgi2024wassa}, the same unit as our replies; because it is peer-reviewed and publicly released, with predictions correlating with human ratings at r = 0.544 on the shared task's test set; and because it comes from a different group, a different dataset and a different model family from every part of our system, so it has no reason to favour it. Its boundaries are also described, such as it is not the most successful system in its common task, it is trained on news articles, not supportive responses, and it produces coarse classes. It is shown in Section 5.4.5 that it does a good job of reproducing the judges' ranking of systems but that it is too noisy on a per-reply basis, so it is only used to compare system averages over the 300 conversations. 

\section{Preliminary Design or Design (Model) Specification}
\label{sec:4.2}

Every design considered is described in this section: the candidates for each component, how each candidate works, and the complete specification of the design finally chosen. What they are is reported here, chapter 5 reports which of them performed best. 

\subsection{Emotion Detector Candidates (d1)}

Five detectors were constructed and trained using the same data and settings, except for the architecture. Table~\ref{tab:4.2} summarises them.

\textbf{GPT-2 Medium (the initial detector):} A 355-million-parameter decoder-only transformer with a classification head on top of its last hidden state. It was the detector for the first pipeline of the project, and was trained on the \textit{situation description} for the event, which was the paragraph a crowdworker wrote before the conversation was started on the data set. There are two properties that make it a weak fit. A left to right decoder will only be able to see each token in the context of tokens that precede it, while classification would benefit from seeing the entire message at once. Also, the situation description is more explicit about the feeling than a person's own message, so a detector trained on the situation learns a simpler task than the one it is presented with in use.

\textbf{BERT-base: }A 110-million-parameter bidirectional encoder pre-trained with masked-language modelling \cite{devlin2019} as the default baseline for sentence classification. Each token will address each other token, and the classification token summarizes the entire message.

\textbf{ELECTRA-base: }An encoder of the same size trained using replaced-token detection, in which the model makes a decision for each token whether it is original or replaced. This is training on all positions, not just the 15\% covered by masking, and can sometimes yield a better encoder with the same compute.

\textbf{RoBERTa-base:} 125-million-parameter encoder trained for a longer period (approximately 160 GB of text) using dynamic masking and no next-sentence objective, and otherwise identical to BERT \cite{liu2019roberta}. It's the size that the memory budget loves, as it leaves nearly all of the 8 GB for the generator.

\textbf{RoBERTa-large: }The 355-million-parameter version of the same model, added to address a cost question, not an architecture question: Is a detector 2.8 times the size worth its training and inference cost in the overall pipeline?

All five are trained with a 32-way classification head, softmax over the emotions, cross-entropy loss, and the training parameters of Section 4.4. Selection was based on top-1 and top-5 accuracy on the 2,542-conversation test partition, where the decision is based on the ranking and not on the best guess, and therefore top-5 accuracy is heavily weighted.

\subsection{Response Generator Candidates (d2)}

Only the generator was changed, and the three were compared with the detector, the prompt, the rules, the conversations and the decoding settings all unchanged. Table~\ref{tab:4.3} summarises them.

\textbf{Qwen2.5-1.5B-Instruct:} The generator of the initial pipeline \cite{qwen2024}. In 16-bit precision it is in the memory budget with 1.5 billion parameters and still has plenty of room to spare, thus being the natural lower bound on generator size.

\textbf{Gemma-3-4B-it:} 4-bit loaded 4-billion-parameter instruction model from a different family. It is a test of the effectiveness of supportive replies with capacity alone. A practical difference that influenced its integration is that it doesn't have a system role in its chat template, which means the instructions need to be incorporated into the user turn.

\textbf{Phi-4-mini-instruct:} The design requires the generator to follow three explicit rules and also to not exceed a word limit, which is why Phi-4-mini-instruct is trained with a strong emphasis on instruction following \cite{abouelenin2025phi4mini} and has 3.8 billion parameters. It is packed with 4-bit NF4 quantisation \cite{dettmers2023qlora} to fit next to the detector.

\textbf{Phi-2 (considered and dropped):} A 2.7 billion parameter model that does not have a chat template. The three rules could not have been enforced without that template because there is no reliable way to separate a system instruction from the user's message without it, and the candidate was dropped before evaluation.

\subsection{Integration Design: How d1's Output Reaches d2}
\label{sec:4.2.3}

The detector will generate a full probability distribution and the connection between the two models is itself a design choice with a number of options (Table~\ref{tab:4.4}). Four of them were applied to the first pipeline: \textbf{argmax }- only the most probable emotion is passed, \textbf{confidence-gated }- the same label is passed but with tentative wording when the detector is not sure, \textbf{distribution }- all the emotions above probability 0.05 are passed, and \textbf{candidate-pick} - the top 3 emotions are passed and the generator is asked to pick one and reply in a single call.

These variants were compared, as described in Section 5.2.4, and the\textbf{ two-stage} design that was used in the final system was developed, where the emotion is selected separately from the writing of the reply. It is motivated by two facts. First, the correct emotion of the detector is one of its three most likely emotions much more often than it is the single most likely, so there is real information in a larger set of candidates. Second, it's that a combination of emotions in one prompt creates conflicting advice; it is not the same to respond well to disappointment as to respond well to impressing. Having the decision in its own short, greedy call removes the uncertainty first, and leaves the generation prompt describing exactly one feeling.

\subsection{Attention-Based Cue Extraction}

In order to make the response address what the person wrote, not just a word for an emotion, the design copies the words that the detector itself used (Figure~\ref{fig:4.3}). Pass the message through the encoder with it being tokenised into pieces and let A ∈ R\textasciicircum{}(H x T x T) be the attention of the last layer, where H is the number of heads and T is the number of tokens. The cue score of token t is the attention that the classification token pays to it, averaged over heads:

s(t) = (1/H) Σ\_h A[h, 0, t]

The sub-word pieces are then restored to words by adding their scores, the special tokens are removed, and the top 40\% of the words are retained (with a minimum of three and a maximum of fourteen words to prevent the generation of an unhelpful cue list from either a very short or very long message). This gives you a few words like "moved away" or "my dog" that you put in the instruction, created by the prompt builder.

One implementation detail is integral, not incidental. The attention implementation must be explicitly requested, as the library's default raises no error and returns no attention weights, in which case it falls back to text splitting. At start-up the system therefore verifies whether weights are returned or not and stops if they are not (Section 3.7).

\subsection{Monolithic and Retrieval Alternatives}

Six designs were tried in which no separate detector was used (Table~\ref{tab:4.5}) to determine if a separate detector is necessary at all. Three prompt the same model to silently detect the emotion, then respond following the same three rules, at 1.5 billion parameters, at 7.6 billion in 4-bit, and with our own 3.8-billion-parameter generator; this latter comparison is the most telling, as it is the same system as proposed but without the detector. A fourth asks the generator to be generic and caring with no emotions whatsoever. A fifth fine-tunes Qwen2.5-1.5B with LoRA \cite{hu2022lora} directly on pairs of user messages and human replies, which tests whether imitating the listeners from the dataset is superior to instructing a model. The sixth is retrieval-augmented \cite{lewis2020rag}: one or two training conversations with the same detected emotion are retrieved with all-MiniLM-L6-v2 sentence embeddings \cite{reimers2019sbert} and shown to the generator as examples of how a person answered.

\subsection{Specification of the Selected Design}

\textbf{Detector:} RoBERTa-base with a 32-way classification head, fine-tuned on first messages with the settings of Table~\ref{tab:4.8}. It reads one message when answering a single message, and the user's last four turns joined together when holding a conversation; Section 4.2.7 specifies the conversational form and Section 5.3.2 gives the measurements behind the four-turn window.

\textbf{Stage 1, emotion choice: }Phi-4-mini reads the message and the three candidates and the three options are shown and the person is asked:\textit{ "An automatic detector narrowed the person's likely feeling down to these options: \{a\}, \{b\}, \{c\}. Read their message and decide which ONE of those options best fits what they are actually expressing. Reply with ONLY that single word."} Decoding takes up to 10 new tokens and is greedy. If the answer does not specify one of the three, the system reverts to the detector's own first choice, but in simulation all answers did specify a valid answer.

\textbf{Stage 2, reply generation:} The system prompt is constructed in a fixed sequence, which consists of the selected emotion, the cue words, the guidance text for the emotion, and the three universal rules (Figure~\ref{fig:4.4}). For lonely, the guidance instructs the model to "acknowledge the isolation itself, gently - the weight of it, not just 'you seem sad'" and not to "offer a surface-level fix like 'go meet people'", and then to acknowledge and validate the feeling in 2-3 sentences, offer reassuring thought specific to the feeling, and end with exactly 1 short question, all within 100 words. There is guidance of this sort for each of the 32 emotions. The decoding settings are as shown in Table~\ref{tab:4.9}.

\subsection{The Conversational Agent}

The evaluation in Chapter 5 responds to one message at a time, while the system that people actually use is a conversation. The agent is the same two-stage pipeline executed once every turn, but with four extra additions that the single-reply system doesn't require (Table~\ref{tab:4.6}).

\textbf{Two memories for two different models: }The detector and the generator are not the same type of model, so they don't receive the same history. The detector is a classifier that was trained on single short messages, so it reads a bounded window (the last 4 turns of the user) and only the user's text, because it was never trained on a listener's reply. The generator is a large-context window model that follows instructions, and is given the full text of the previous ten exchanges in the conversation, which if summarised would remove the emotional detail that the reply relies on. The attention cue(s) are from the current message, not from something they have gone past.

\textbf{Rules that change after the first turn:} The three response rules are kept the same as they are measured in this thesis, and this is why the first turn is comparable with every single-turn result in Chapter 5. Starting from the second turn, the question is no longer compulsory, the generator is asked not to repeat an answer it has already given (which is an acknowledgement), and the generator is told not to use the same phrasing as in its previous answers. Every turn, a question, no matter how well-intentioned, makes a conversation an interrogation.

\textbf{Emotions that move: }The emotion of each turn is compared to the emotion of the previous turn. If it does, it will say what it changed to and ask for a response to what the person feels now, since it would sound like they didn't listen if they were to respond to the initial prompt.

\textbf{Audit trail for each turn: }agent writes down the detector's three candidates and their probabilities, the emotion selected in stage 1, the cue words, if the emotion changed, and the response. It prints this before each reply and can export the entire conversation. The argument that threads its way through this thesis is that an end-to-end model can generate the same response, but it can't demonstrate which feeling it responded to, nor can it provide for any intervention prior to the response.

\section{Data Collection and Preparation}
\label{sec:4.3}

\subsection{Source of the Data}

All data is taken from EmpatheticDialogues \cite{rashkin2019}, a corpus where one crowdworker describes a situation related to one of 32 emotions, and the other one responds as a listener. The released files contain 23,144 conversations and 88,687 utterances, already split into training, validation and test sets, with the property that all conversations initiated by the same speaker are within a single set, thus preventing the leakage of a speaker's style from training to test. The corpus is used under its non-commercial research licence \cite{ed_github}. The route from those files to the four datasets this work actually uses is indicated in figure 4.6.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.95\linewidth]{figures/ch4_fig6.png}
\caption{From the released corpus to the datasets used in this work}
\label{fig:4.6}
\end{figure}

\textbf{Why not GoEmotions: }the project started on GoEmotions \cite{demszky2020} and the first months went into preparing it: 54,263 Reddit comments from 27 emotions and a neutral class, processed to a 28-label multi-label set, analysed, and then rewritten as dialogue with templated replies. It was abandoned for four reasons, all based on that prepared data, not as assumptions.

1.\textbf{ It has no replies:} A comment has only a label and not much else, so there's nothing to train or evaluate a response generator against. The responses that we generated for it were our own, so any system trained on them would just be learning our language back.

2.\textbf{ A third of it has no emotion to answer:} The class \textit{neutral }is the largest with 32.75\% of the corpus. A support system is not requested to react to 18,000 neutral comments.

3.\textbf{ The emotions it does carry are the wrong ones:} Its frequent classes are reactions to online comments, with \textit{admiration }at 9.4\%, \textit{approval }at 6.8\% and \textit{amusement }at 5.3\%, while the states a support conversation actually has to answer are its rarest: \textit{grief }appears 96 times against \textit{admiration}'s 5,122, a ratio of 53 to 1, and the set has no \textit{lonely}, \textit{devastated}, \textit{terrified }or \textit{apprehensive }at all.

4.\textbf{ Its labels overlap: }16.25\% of examples have more than one emotion, most frequently \textit{anger }and \textit{annoyance}, which is not compatible with the design that conditions one response to one emotion.

EmpatheticDialogues answers all four: each conversation is a first-person disclosure that can be replied to, it includes the listener's reply, it contains exactly one of 32 emotions chosen by the speaker before writing, and those 32 are the states a support conversation is made of. The GoEmotions work is stored in the repository, and the change of corpus is the reason why the project's own labels are the 32 used throughout this thesis instead of the 28 as planned.

\subsection{Data Cleaning}

There are three cleaning steps, each of which is for a particular defect on the released files. The literal string \_comma\_ is stored in the corpus and restored to a comma, which in place would look as follows: inside the text that a model reads, and inside the text that a rater sees in the replies. If a row doesn't parse as a valid CSV (a few due to unescaped quotation marks), it is ignored and not modified, since a partially parsed utterance should not be trusted. Any row with an empty utterance or an empty emotion label is removed as neither can be used for supervision. The text and the label are trimmed of surrounding whitespace. 

\subsection{Data Reduction}

The detector is asked to read one message in the entire conversation, recorded in the corpus. The first utterance in each conversation is stored (along with the emotion label for that conversation), while all other utterances in the conversation are removed. This single decision is the most important preparation decision in the project and here it takes the place of the initial choice of training on the \textit{situation description }with the pipe-line. The description is provided following the event and the feeling is named almost explicitly, so training on the description is a somewhat easier task than what the detector needs to do, and Section 5.2.2 quantifies the price paid for that mismatch.

One conversation before and after the entire preparation is shown in figure 4.7: released rows on the left, single labelled row that reaches the detector on the right.

A second reduction is used to specify the evaluation set. The quality of the replies is evaluated on the 300 conversations in the test partition for seed 42, and all generation experiments in this thesis do so. Of these, 64 (2 for each emotion) are selected, the two shortest and two longest messages in each emotion, resulting in all emotions having representation within the judges' daily request limits. 

\subsection{Data Transformation}

Text is only transformed to the extent needed in each model. Messages for the detector are tokenised using the model's own tokeniser and then truncated to 128 tokens, which covers 99.7\% of first messages with an average length of 46.5 tokens; the 32 emotion names are also mapped to integer labels in a fixed order, to ensure that predictions are comparable across candidates. Except for Gemma, the users message is inserted in the model's chat template, with the system prompt of Section 4.2.6 in the system role, no truncation is applied to the users message, but to the generators. The models are pre-trained on natural text and no lower-casing, stemming or stop-word removal is used anywhere because they would remove the very cues, including capitalisation and punctuation, that indicate feeling. 

\subsection{Data Integration}

For the response experiments, two types of records are combined. For each evaluation conversation, a pair of the user's initial message and the human listener's response is added, with the human listener's response only being kept as a reference for reading and not as a target for which the systems are evaluated. These generated replies are then re-joined with their conversation with conversation identifier, so that the reply, the gold emotion, the detector's prediction, the automatic rule checks and the AI-judge scores are all in one row. This one row per reply structure is the reason that the paired statistical tests in Chapter 5 are possible: two systems can be compared one conversation at a time, not just in aggregate.

\section{Implementation of the Selected Design}

\subsection{Detector Training}

Every detector candidate was optimised end-to-end with a cross-entropy loss for the 32 emotions using the set-up of Table~\ref{tab:4.8}. Training is for at most 4 epochs with early stopping after 1 epoch with no improvement, and the checkpoint reported is not the last because if the run starts to over-fit, it gets discarded in the statistics. The learning rate warms up linearly over the first 6\% of steps: this is the same fine tuning procedure used on RoBERTa, and is not cosmetic, as without it, the RoBERTa-large run diverged to 5.0\% accuracy until the cause was discovered (Section 3.7). A mixed precision of 16 bits and gradient accumulation ensures that 16 batches fit in 8 GB of memory. All five candidates were trained using the same script with the only difference being the model name, and the seed used in every run was 42, so it is a comparison between the architectures, not the training recipes.

\subsection{Generator Configuration}

The generator is never trained in the final system; it's used zero-shot and is steered solely by its system prompt. That's possible in the memory space due to two implementation decisions. To maintain the quality of 16-bit weights, the model is loaded with 4-bit NF4 quantisation and double quantisation with 16-bit computation \cite{dettmers2023qlora} which reduces the memory by approximately 4X. Decoding is always done for all systems in the thesis with sampling at temperature 0.7 and top-p 0.9, but not with greedy or beam search, because they have been known to generate repetitive text \cite{holtzman2020}. The settings are the same for all locations and any disparity between the systems is due to design choice and not to decoding.

\subsection{Implementing the Two Stages}

Stage 1 calls for at most 10 tokens and it tests the answer by comparing it with the three possible names: if it doesn't match any of the three, it reverts to the detector's first guess. In stage 2, the system prompt is built in the sequence as shown in figure 4.4 and the sampling call is set to 250 new tokens, which is more than the prompt's request of less than 100 words, to make sure that no reply is cut off mid-sentence; the longest reply the final system generated was 119 tokens. There are also three model-specific details that need to be handled explicitly and can otherwise silently corrupt results if omitted: Phi-4-mini's end-of-turn token differs from its end-of-text token, and thus generation should stop on the former; Gemma does not have a system role in its chat template; and Phi-4-mini merges its attention projections into a single layer, which matters when naming the modules to target in low-rank adaptation. 

\subsection{Implementing the Baselines}

The difference between the monolithic baselines is simply the fact that the same 300 conversations, decoding settings, rule checks and output format, but without the detector, and the prompt asking the model to work out the feeling itself. LoRA baseline is the one design which is training a generator with rank 16 and alpha 32 with attention projections, and a learning rate of 2e-4, which are the values used in the original low-rank adaptation work \cite{hu2022lora}. It has one correction to note -- the padding token should be the model's end of text token, as using the end of turn token will remove that token from the loss and if the model never sees it, it learns not to stop. This was the same with the first version of this baseline; it was retrained when this defect was discovered and every involved number was replaced (Section 5.3.3).

\subsection{Verification and Safeguards}

Before a full evaluation a small trial run was conducted to check that the output of every design was well formed, and that the above model specific details were accounted for. Two automatic safes are then implemented to guard the chosen design in typical operations: if the detector doesn't return any attention weights, the cue mechanism won't break without the user being aware of it; every choice made on stage-1 is also stored in the output file, so a wrong formation of the emotion choice will be noticed, not swallowed by the fallback. The repository also contains scored outputs for all 4,200 generated replies, making it possible to recreate all tables in Chapter 5 with a script rather than human hands.
